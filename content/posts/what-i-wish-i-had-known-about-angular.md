Making the jump from vanilla JavaScript to a library like jQuery is _refreshing_. "You mean I don't have to \_\_\_\_ anymore ??" These libraries are really meant to help and smooth over some coding rough edges. Frameworks like Angular are nothing like that. At all. They aren't meant to smooth over rough edges, they're meant to expand the capability of the language. That's the practical way of looking at it. The technical way of looking at it is, "Everything Angular accomplishes it does through JavaScript, and it's really opening up a very advanced usage of what's already there, smoothing over the rough edges of getting to that level." But again, for the average JavaScript programmer, switching to Angular (or React or similar) is not about making things easier, it's about making things better and more advanced. Having spent the last month or two diving into Angular for a few real-world apps, here is what I wish I had known going in. Perhaps this will be helpful to some other "JavaScript ninjas" who are making the transition to the full framework of Angular.

*   **Angular is not AngularJS.** AngularJS was the first version, and was used more or less like any other library. You included the whole library, wrote your "angular" code as part of your output files, and when the user visited it "sort of" compiled your code on the fly. Angular 2 (and 3,4 etc.) is usually precompiled. You have a whole project full of files, and you compile them down into an output JavaScript file. I think there are two advantages here. First, you get a better framework for advanced developing, separating your project out into appropriate pieces and keeping a helpful file structure. Second, the Angular compiler doesn't have to run every time the user comes, and only the pieces that are needed are used.
*   **You need a solid knowledge of ES6 first.** You could get away with avoiding some features (like "let" and arrow functions) but not all of them. It relies heavily on JavaScript modules and class syntax.
*   **If your app will have asynchronous elements, plan those out first**_._ The most obvious example are database and API requests, which take an unspecified amount of time to complete. You'll need to have the rest of your app accommodate those requests and if your app structure doesn't support it, you'll end up rewriting large chunks. If you've never dealt with asynchronous code, Angular is probably not the place to start. First read about JS promises, then Angular Observables, then Subjects and Behavior Subjects. Code real examples of each of those and then move on to the next. Get through all 4 and you'll be golden.
*   **Don't confuse ES6 modules with Angular modules.** ES6 modules are about separating your code into files, letting the files reference each other, and encouraging OOP practices. Angular modules are how the pieces your app are separated and connected.
*   **Also, don't confuse JavaScript imports and exports with module imports and exports**. They're largely unrelated. JavaScript imports (usually at the top of the file) and exports (usually before declarations like classes) let the code in different files _see_ each other. Angular module imports and exports let the different pieces of your application _use_ each other. There's some overlap.
*   **Take advantage of the Angular CLI.**_ _ The command line interface will generate many elements for you, and more importantly, it will do it _right_. It's a push in the right direction of best practices, including unit testing, naming conventions, and file management.
*   **The view hierarchy is different from your application hierarchy.** The view hierarchy is how the user moves from section to section of your app, while the application hierarchy is how you've structured the code of your application. A user might drill down from one component into another, but those components might not necessarily be parent-child components in your code. However, they often _can_ be as it makes sense to structure your application into logical sections.
*   **Understand how the scope of Angular's application hierarchy works.** Components are contained within modules, and can only see other components that are exposed to it by the module. But modules can (usually) all see each other. The Angular compiler actually puts all the modules together except in certain circumstances.
*   **Think of providers as single instance classes.** If different parts of your app need to talk to each other, they can do it through a "service". These are the stable islands amidst your application's shifting seas. Need to track data throughout your app? A service can be your application's data model.
*   Finally, and this applies to most programming learning, **don't try and go through an entire training program or online course without getting your hands dirty**. The pieces won't conceptually fall into place until you've tried to do them wrong over and over, and finally get it right.
