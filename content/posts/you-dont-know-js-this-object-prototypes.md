JavaScript has a reputation for being a novice-friendly language. While a developer of another language, say C#, might study the entire system under the hood, a JavaScript developer might only learn "the good parts" he or she needs to "get the job done." This is a strength of the language as it really makes programming accessible (see, for instance, the Minecraft JavaScript programming camps). However for the serious developer it is also a weakness. You can't _really_ become a proficient, advanced developer without diving deeper. Trying to do advanced JavaScript without exploring the "deep parts" is a bit like paying no attention whatsoever to politics but then voting once every 4 years. Sure you can do it, but you'll have no idea what's really going on and the results will be unpredictable. That's why I'm so fond of Kyle Simpson's _You Don't Know JS_ series. It's specifically geared towards those developers who are ready to dive deeper. In his third volume he focuses on "this" and objects in JavaScript. I've previously written about [the complexities of "this" in JavaScript](https://www.tmdesigned.com/actually-understanding-this-in-javascript/), but objects deserves their own writeup as well. Kyle begins his chapter on objects by countering the common belief that in JavaScript "everything is an object". This is true in practice (truthy?) but not what's really happening. Primitives like string and number are not objects, but are instead "coerced" into their counterpart object forms when used as such (String, Number, etc.; notice the capitalization). Objects, on their face, are essentially a set of key:value pairs. As those values can themselves be objects, or even references to other objects like functions, their complexity can grow quickly. Importantly, objects are passed by reference, not by value. \[code language="javascript"\]var objA = { a : 5 }; var objB = objA; objA\["a"\] = 6; console.log(objB.a); // 6 \[/code\] In this example changing objA's property also changed objB's. (Also, notice the two separate ways of accessing the property.) This key:value setup is enough information for most JavaScript developers to pass along basic information and work with JSON data. However, that's just the tip of the iceberg with objects. Extending the behavior of objects being passed by reference, we run into the main limitation of using the Object Oriented Programming model with JavaScript. Classes in OOP imply--_demand_\--true copies be made. Children classes must be able to overwrite their parent's functions ("polymorphism") yet generally still be able to access them. With JavaScript, though, the child and parent share a reference to the same objects. The child class cannot overwrite the parent, and so the idea of "extending" a class is largely lost. Methods that attempt to simulate this (manually extending classes) will yield partial success but add a lot of bloat. Kyle uses the typical example, a parent class (Vehicle) and child class (Car), to illustrate this well. If Car has a drive() function that also needs to call the parent Vehicle class's drive() function, it ends up looking like this: \[code language="javascript"\] drive(){ Vehicle.drive.call(this); ...//additional code } \[/code\] The reason for the obscure function call is twofold. First, we have to use Vehicle.drive instead of just drive so that the parent's function is called instead of the current one. But then, anything the function does is bound to Vehicle, and presumably we want to be operating on Car. So we have to use the explicit .call() technique to specify our context. This brings us to the \[\[Prototype\]\] chain. While the class model relies on _copies_, the prototype functionality of Javascript uses _links_. We simply establish an inheritance pattern, a chain, that JavaScript will traverse when needed. But again, no copies are made. \[code language="javascript"\] var spaceship = { currentWarpSpeed : 0, targetWarpSpeed : 1, engage : function(){ currentWarpSpeed = targetWarpSpeed; } } var Enterprise = Object.create(spaceship); console.log(spaceship); // Object {currentWarpSpeed:0,targetWarpSpeed:1,engage:function} console.log(Enterprise); // Object {} console.log(Enterprise.targetWarpSpeed); // 1 \[/code\] In this example, Enterprise and spaceship are linked on the prototype level by the Object.create technique. Enterprise the object is still empty, yet when attempting to access the target warp speed we still get a result of 1. JavaScript looked at Enterprise first, didn't find anything, and then looked higher up the chain. Is Enterprise extending spaceship? It sort of looks like it, but not truly. If Enterprise gets its own engage() function, it will just "shadow" the parent's engage() and take precedence over it. This prototyping opens the door to some really cool techniques (but not fully the class model). One common usage is with the new operator. \[code language="javascript"\] function Borg(){ this.isInTheCollective= true; } var taylor = new Borg(); console.log(taylor); // Borg { isInTheCollective:true } \[/code\] Taylor is an object, but is an instance of Borg so it displays with that label in the console. Using the "new" operator has several effects, including creating a new object, using that new object for any "this" calls in the function referenced, and returning that object. A fourth effect, though, is that a prototype link is established. \[code language="javascript"\]function Borg(){ this.isInTheCollective= true; } var taylor = new Borg(); Borg.prototype.hiveMind = true; console.log(taylor.hiveMind); // true \[/code\]So again, when JavaScript's engine can't find "hiveMind" on taylor, it looks up the prototype chain, which in this case includes Borg. (Every function has functionName.prototype, and it is this that objects created with "new" are linked.) So Javascript provides a lot of helpful, advanced functionality for working with objects. But one thing Kyle Simpson stresses again and again in his book is that these capabilities do not add up to true classes. A passing review of some of this might lead one to believe that (i.e. prototype linking has some overlap with class-based inheritance) but that's just the kind of incomplete, vague knowledge that gets JavaScript developers in trouble.
