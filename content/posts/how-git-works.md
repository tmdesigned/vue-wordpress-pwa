In preparing a training series on git, I previewed 6 different video courses to try and identify the best approach to understanding git. I did this in an effort to spare others from the learning pains that are so common when diving into version control. You can read about commits, merges, rebasing, pulls, and so forth a hundred times but until you start messing with it, until you get it _wrong_ a bunch of times, it doesn't start to click. I found the available courses lacking, because they are taught from the perspective of someone who (naturally) already understands git. They struggled to find a balance between explaining how git "thinks" and using git as a black-box. The closest courses to successfully explaining git and providing the right foundation are by Paola Perrotta: How Git Works and Mastering Git. How Git Works is fascinating, because he peels back the layers of the onion that is git, explaining each component bit by bit. He starts with the SHA algorithm, which is a truly fascinating topic. In developing my own learning resources, I created an approach based on Perrotta's. Say you had two cloth bags, full of dozens of items and quite bulky and heavy. How could you tell if the two bags contained the same contents? The obvious answer is to take the contents out and compare them. How laborious! What if you didn't have to be certain, just reasonably confident? Would there be a faster way? Sure -- you could compare the shape of the bags, and more importantly their weight. If they were exactly, down to 1/10th of a gram, the same weight, you might say you were reasonably confident the contents were the same. Of course, different things can weigh the same. But what if they couldn't? That's the advantage behind SHA. It's a way for the computer to _very quickly_ get the 'shape' of a file. But unlike weight, no two things will have the same SHA. So now we have a way for a computer to (a) see if a file has changed, and even (b) see if two different files have the same exact contents. This is really the root of all of git. Without SHA, if you had 1,000 revisions of a project, the computer would store a copy of _each file_ for _each revision_. Many of the files in those 1,000 revisions would be exactly the same, but the computer wouldn't know. But with SHA, it only has to track _unique_ files. Perrotta wisely expands out from this core point, explaining how directories also have a SHA "hash", as does each commit. He rips the veil off of the .git directory, showing what it actually is -- a collection of file content objects ("blobs") and of other objects showing their relationship -- both to each other, and across time. True, knowing how git works does not tell one how to use it. But it does set the proper foundation. It means that from then on in your training whenever you use words like "commit" and "hash" you can have a realistic mental image of what they are. Perrotta's approach is the winner, and I hope my own training resources I develop from this approach build on his work in the same clear, helpful manner.
